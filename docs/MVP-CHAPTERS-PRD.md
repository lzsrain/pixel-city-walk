# Pixel City Walk｜济南六章节 MVP PRD（冻结版）

- 文档状态：Frozen / 可直接进入设计与开发
- 版本：MVP Chapters v1.0
- 冻结日期：2026-08-13
- 目标仓库：`pixel-city-walk-product-lab`
- 产品负责人：产品经理
- 交付原则：先交付可识别的济南视觉与两章完整闭环，不用功能数量掩盖图片质量

## 1. 结论

本期将现有“一张抽象济南地图自由漫游”升级为“济南像素城市册”：

1. 首页展示一张济南六章节总览图；
2. “泉城老城”和“明府城·大明湖”两章可以进入、漫游、收集并完成；
3. “百年商埠、山城济南、黄河济南、新城济南”四章只展示主题封面和代表地标，标记为即将开放；
4. 玩家完成每个可玩章节后，生成一张章节专属像素明信片；
5. 地图、章节封面、场景标记、收藏册和明信片必须复用同一套地标像素母稿，禁止分别生成互不一致的图片；
6. 拼豆本期完全下线，不作为入口、奖励或开发任务。

本期只验证一个核心假设：**用户是否愿意完成一段济南像素漫游，并因为路线与收集结果下载一张具有济南辨识度的章节明信片。**

## 2. 现状与问题

### 2.1 当前已经可复用

经代码与素材检查，当前项目已有：

- 无构建步骤的静态网页架构；
- `city.json` 城市数据与 `engine.js` 引擎的初步分离；
- 1536×1024 城市地图画布；
- 键盘、鼠标、触屏移动；
- 景点故事弹层、收集手账和本地进度保存；
- 1672×941 明信片底图、Canvas 动态文字与 PNG 下载；
- 玩家昵称、到访路线、收集统计与分享入口；
- 一张济南地图、六个区域和十三个可收集场景。

### 2.2 当前必须解决

- 现有地图更像泛中式水城，不足以代表济南；
- 所有区域被放入同一张可步行地图，真实空间关系、尺度与产品层级混在一起；
- `routeDefs` 写死在 `engine.js`，无法由城市包配置章节和路线；
- 全城共用一张 `map.png` 与一张 `ticket-base.png`，不能输出章节差异；
- 图片各自生成，没有稳定的“地标母稿 → 地图/封面/明信片”复用链；
- 拼豆原型造成产品主线偏移，且当前质量不具备公开展示条件。

## 3. 产品定位与目标用户

### 3.1 一句话定位

把济南的真实特色区域做成可以行走、收集并带走章节明信片的像素城市册。

### 3.2 首要用户

- 在小红书、GitHub 或朋友分享中第一次打开项目的轻度玩家；
- 喜欢像素风、城市旅行、数字集章和地方文化内容的人；
- 济南本地人及到访过济南、对地标辨识度敏感的人。

### 3.3 核心用户故事

> 作为第一次打开项目的用户，我想快速看懂济南由哪些有差异的城市章节组成，并完成其中一章的像素漫游，以便获得一张能证明“我走过了什么”的济南专属明信片。

## 4. 成功指标

### 4.1 北极星指标

**章节明信片生成率**：进入任一可玩章节的用户中，成功打开该章完成页并生成明信片的比例。

### 4.2 MVP 观察指标

- 总览页 → 可玩章节进入率；
- 可玩章节开始 → 完成率；
- 完成页 → 明信片下载率；
- 两章都完成的用户比例；
- 首次打开至完成一章的中位时长；
- 图片加载失败数和初始化错误数。

静态 MVP 不接入后台统计时，必须保留可插入事件埋点的统一函数接口；本期可先用开发模式控制台事件验证漏斗。

## 6. 页面与核心流程

### 6.1 S0 启动页

目的：在 5 秒内让用户明白产品不是导航地图，而是一套可收集的济南像素章节。

必须包含：

- 产品名“泉城漫游记”；
- 一句说明：“走进济南六个章节，收集你的像素城市册”；
- 主按钮“进入济南”；
- 可选昵称输入，默认“旅行者”，不阻断进入；
- 六章节总览的局部视觉预告。

不再出现：拼豆、纪念物组装、先选路线等旧文案。

### 6.2 S1 济南六章节总览

目的：呈现济南“南山—城中泉湖—北部黄河—东西城市发展”的章节结构，而不是承担真实导航。

必须包含：

- 一张 1536×1024 像素总览图；
- 六个章节入口，每个入口有名称、代表地标和状态；
- 两个可玩章节使用高亮、轻动画或脉冲标记；
- 四个锁定章节降低亮度，显示“即将开放”，点击后打开章节预告而不是无响应；
- 城市册入口与当前进度，例如“0/2 张已获得”；
- 返回启动页或重新开始入口。

总览图是章节选择界面，不绘制可步行道路，也不在这一层显示十几个景点针脚。

### 6.3 S2 章节介绍卡

用户点击章节后打开，不直接把角色丢进地图。

可玩章节必须显示：

- 章节封面；
- 章节名与一句主题文案；
- 本章代表地标数量；
- 预计体验时长“约 6–10 分钟”；
- 本章明信片预览轮廓；
- “开始漫游”按钮。

锁定章节必须显示：

- 章节封面与 2–3 个代表地标；
- “即将开放”；
- 返回总览按钮；
- 不显示虚假可用日期，不收集通知或手机号。

### 6.4 S3 区域漫游地图

沿用现有 Canvas 行走、点击移动、WASD、方向键、触屏和场景标记能力。

每章必须满足：

- 独立区域地图；
- 5–6 个可识别地标；
- 每个地标至少 1 个故事点；
- 桌面端可行走，移动端可直接点地标打开内容；
- 顶部显示章节名、已收集数量、返回总览；
- 玩家可以随时结束，但只有达到完成条件才获得章节明信片；
- 地图只作为艺术化漫游空间，必须保留“非导航地图”说明。

### 6.5 S4 景点故事与收集

沿用当前故事弹层和“收进手账”操作，文案每个景点控制在一屏内。

每个地标内容包括：

- 地标名称；
- 50–100 字故事正文；
- 两个短事实字段；
- 一张从共享母稿导出的景点图或地图局部；
- “收下这枚印章”和“继续走走”。

本期不增加多分支选择、对话树、道具合成或数值系统。

### 6.6 S5 章节完成页

触发条件：收集本章规定的必收地标；默认要求 5 个，具体见章节定义。

必须包含：

- 章节完成标题；
- 已收集地标与路线摘要；
- 章节明信片实时预览；
- 昵称编辑；
- “下载明信片”主按钮；
- “回到城市总览”和“继续补收集”次按钮；
- 下载成功后更新城市册状态。

### 6.7 S6 城市册

城市册共六个固定卡槽：

- 可玩章节已完成：显示实际明信片缩略图，可重新下载；
- 可玩章节未完成：显示章节轮廓与“完成本章获得”；
- 锁定章节：显示封面剪影与“即将开放”；
- 进度显示为“已获得 X/2”，不能写成 X/6 误导用户当前可以全部完成。

## 7. 章节范围（冻结）

### 7.1 六章节总览

| 顺序 | 章节 ID | 章节名 | MVP 状态 | 代表视觉 | 点击结果 |
|---|---|---|---|---|---|
| 1 | `quancheng-oldcity` | 泉城老城 | 可玩 | 三股泉涌、泉标、三虎吐水、护城河 | 章节介绍卡 |
| 2 | `mingfu-daming` | 明府城·大明湖 | 可玩 | 老城泉渠、荷花湖面、超然楼夜景 | 章节介绍卡 |
| 3 | `historic-commercial` | 百年商埠 | 锁定 | 经三路老建筑、小广寒、梧桐街道 | 章节预告卡 |
| 4 | `mountain-jinan` | 山城济南 | 锁定 | 千佛山、佛慧山、灵岩寺 | 章节预告卡 |
| 5 | `yellow-river` | 黄河济南 | 锁定 | 黄河、鹊山、华山、黄河大桥 | 章节预告卡 |
| 6 | `new-jinan` | 新城济南 | 锁定 | 奥体中心、CBD、云鼎大厦 | 章节预告卡 |

章节总览只表达城市结构，不承诺行政区全覆盖。章丘、莱芜、平阴、长清不进入本期六章节，也不在界面以第七章形式出现。

### 7.2 可玩章节 A：泉城老城

- 主题：泉从城中涌出，也流进济南人的日常。
- 区域主色：泉蓝、柳绿、米白、少量朱红。
- 预计时长：6–10 分钟。
- 必收 5 个：趵突泉、五龙潭、泉城广场、黑虎泉、解放阁。
- 可选 1 个：护城河水路。
- 完成条件：5 个必收地标全部收集。
- 章节明信片：`spring-city-postcard` / “泉水线明信片”。

建议漫游顺序只作体验引导，不称为现实导航路线：

```text
趵突泉 → 五龙潭 → 泉城广场 → 黑虎泉 → 解放阁 → 护城河
```

必须保留的识别特征：

- 趵突泉：三股白色泉涌、临水亭阁；
- 五龙潭：开阔潭面、水榭、柳树，不能画成另一个趵突泉；
- 泉城广场：蓝色“泉”字泉标；
- 黑虎泉：三只虎头与三股出水；
- 解放阁：厚重城台和双层飞檐；
- 护城河：连续水路、柳岸与小型游船。

### 7.3 可玩章节 B：明府城·大明湖

- 主题：泉水穿过老城，最后汇进大明湖的昼夜。
- 区域主色：深湖蓝、荷叶绿、暖金、灰瓦色。
- 预计时长：6–10 分钟。
- 必收 5 个：曲水亭街、百花洲、珍珠泉、大明湖、超然楼。
- 可选 1 个：芙蓉街。
- 完成条件：5 个必收地标全部收集。
- 章节明信片：`lake-night-postcard` / “湖城夜游明信片”。

建议漫游顺序：

```text
珍珠泉 → 芙蓉街 → 曲水亭街 → 百花洲 → 大明湖 → 超然楼
```

必须保留的识别特征：

- 曲水亭街：泉渠沿街、石桥、灰瓦老屋；
- 百花洲：水院、荷叶、临水民居；
- 珍珠泉：规则泉池与串珠状泉泡；
- 芙蓉街：窄街、老招牌、烟火气，不画成现代商业街；
- 大明湖：开阔湖面、荷花、游船与远岸；
- 超然楼：七层重檐、暖金夜景、湖面倒影。

## 8. 共享视觉资产规范

### 8.1 核心原则

每个地标只能有一个视觉母稿。地图、章节入口、故事卡和明信片全部由母稿导出，不允许针对不同页面重新生成一座不同外形的建筑。

```text
地标像素母稿（唯一真源）
  ├─ overview：六章节总览小图
  ├─ map：区域地图地标精灵
  ├─ story：景点故事卡插图
  └─ postcard：章节明信片组合素材
```

### 8.2 目录与命名

建议目录冻结为：

```text
cities/jinan/assets/
├─ overview/
│  ├─ jinan-chapters-map.png
│  └─ chapters/
│     ├─ quancheng-oldcity-cover.png
│     └─ ...
├─ chapters/
│  ├─ quancheng-oldcity/
│  │  ├─ map.png
│  │  └─ postcard-base.png
│  └─ mingfu-daming/
│     ├─ map.png
│     └─ postcard-base.png
└─ landmarks/
   ├─ baotu/
   │  ├─ master.png
   │  ├─ map.png
   │  ├─ story.png
   │  └─ postcard.png
   └─ ...
```

目录名使用稳定英文 ID；用户可见名称全部来自数据文件。

### 8.3 图片交付规格

| 资产 | 数量 | 最低规格 | 背景 | 用途 |
|---|---:|---|---|---|
| 六章节总览图 | 1 | 1536×1024 PNG | 不透明 | 章节选择主画面 |
| 章节封面 | 6 | 960×540 PNG | 不透明 | 介绍/预告卡 |
| 可玩章节区域地图 | 2 | 1536×1024 PNG | 不透明 | Canvas 漫游 |
| 地标母稿 | 12 | 长边 ≥1024 PNG | 透明 | 视觉唯一真源 |
| 地标地图版 | 12 | 96–192 px 级 PNG | 透明 | 区域地图与总览 |
| 地标故事版 | 12 | 640×360 或正方形 PNG | 可透明 | 故事卡 |
| 明信片底图 | 2 | 1600×900 PNG | 不透明 | Canvas 动态叠字与下载 |
| 明信片预览缩略图 | 2 | 480×270 PNG | 不透明 | 城市册与章节介绍 |

注：12 个地标即两章各 6 个；同一母稿导出多尺寸不计为新增设计。

### 8.4 统一画风

- 正视或轻微俯视的手绘像素插画，不混用写实照片、3D 渲染和等距城市素材；
- 清晰硬边像素，不使用会产生糊边的缩放；
- 建筑轮廓、屋檐层数、泉眼数量等标志性结构必须正确；
- 水使用统一的深浅两级以上蓝色，夜景统一使用暖金灯光；
- 总调色板建议控制在 32–48 个共享颜色；
- 图片内不烘焙标题、日期、昵称、路线和按钮文字，所有文字由页面动态绘制；
- 不照搬游客照片构图；参考资料和生成素材的许可必须记录在 `ASSET_LICENSES.md`。

### 8.5 图片优先交付顺序

为保证用户后续只能使用纯文本模型时仍有完整图片资产，本期图片按以下顺序交付，不等待全部功能完成：

1. 视觉基准：超然楼、趵突泉、黑虎泉 3 张地标母稿；
2. 泉城老城 6 个母稿 + 区域地图 + 明信片；
3. 明府城·大明湖 6 个母稿 + 区域地图 + 明信片；
4. 六章节总览图；
5. 四个锁定章节封面。

每完成一批立即写入正式目录并由浏览器实装验证，不把图片只留在聊天或临时目录。

## 10. 功能范围与不做项

### 10.1 Must（MVP 必须做）

- 六章节总览与六个章节入口；
- 两个可玩、四个锁定；
- 两张独立区域地图；
- 两章各 6 个地标，5 个必收；
- 两张章节专属明信片；
- 城市册六卡槽与 0/2 真实进度；
- 图片共享母稿机制和正式目录；
- 本地进度 v2；
- 桌面与移动端完整流程；
- 素材许可记录；
- 真实浏览器逐流程验收。

### 10.2 Should（不阻断首个可玩包，但应在本期完成）

- 锁定章节预告卡；
- 明信片 Web Share API 分享与不支持时下载降级；
- 控制台漏斗事件；
- 资源加载占位与失败提示；
- 第一章完成后引导尝试第二章。

### 10.3 Could（有余量再做）

- 地标收集后的轻量盖章动画；
- 总览图水系或灯光的低成本循环动画；
- 一键重下已获得明信片；
- 两章完成后的城市册完成纪念封面。

### 10.4 Won't（本期明确不做）

- 拼豆、十字绣、钻石画及实体周边图纸；
- 章丘、莱芜、平阴、长清等扩展章节；
- 让另外四章变成可玩地图；
- 登录、云存档、排行榜、评论和账号体系；
- GPS、实时位置、导航、门票与路线推荐；
- AI 在线生成图片或上传照片生成像素画；
- 多分支剧情、复杂 NPC 对话、身份结局和道具合成；
- 城市包可视化编辑器；
- 后端、数据库或新前端框架迁移；
- 重写角色移动引擎；
- 在图片内写死中文标题或玩家昵称。

## 12. 验收标准

### 12.1 产品流程

- [ ] 首次打开后，用户在两次点击内到达六章节总览；
- [ ] 总览稳定显示 6 个章节，且只有 2 个标记为可玩；
- [ ] 点击 4 个锁定章节均出现预告卡，不进入空地图、不报错；
- [ ] 两个可玩章节都能独立进入、行走/点击、打开故事和收集；
- [ ] 每章收集 5 个必收地标后才出现获得明信片的完成态；
- [ ] 未完成章节时可以退出，但不会错误解锁明信片；
- [ ] 完成第一章不影响第二章的独立收集进度；
- [ ] 城市册准确显示已获得 X/2，而不是 X/6；
- [ ] 页面不再出现任何拼豆入口、弹层、介绍或下载按钮。

### 12.2 图片与济南辨识度

- [ ] 不看标签时，趵突泉、泉标、黑虎泉、解放阁、超然楼至少可通过标志性轮廓或元素区分；
- [ ] 趵突泉有三股泉涌，黑虎泉有三虎吐水，超然楼保持七层重檐；
- [ ] 两章地图在色彩与构图上明显不同，不能只是替换标题；
- [ ] 地图中的地标、故事卡和明信片使用相同母稿导出，结构不漂移；
- [ ] 地标在常用手机尺寸上仍可看清，不依赖放大后才能辨认；
- [ ] 明信片不把昵称、日期、路线等动态文字烘焙进底图；
- [ ] 图片无临时路径引用、无 404、无跨域依赖；
- [ ] 每张第三方参考或非原创素材都在许可文件有来源记录。

### 12.3 明信片

- [ ] 两个章节下载的背景、章名、主色和地标组合明显不同；
- [ ] 下载 PNG 至少 1600×900，昵称、日期、章节名、路线和收集数不越界；
- [ ] 文件名包含济南、章节与明信片，不含非法文件名字符；
- [ ] 用户修改昵称后，预览和下载内容同步更新；
- [ ] Web Share 不可用时自动下载，不出现死按钮。

### 12.4 技术与兼容

- [ ] `python -m http.server` 启动后无构建步骤即可体验；
- [ ] Chrome 桌面端全流程通过；
- [ ] 390×844 竖屏和 844×390 横屏核心流程可操作；
- [ ] 刷新后昵称与章节进度保留；
- [ ] 旧 `v:1` 存档不会导致新章节被错误完成；
- [ ] 初始化和图片加载失败时提供可理解提示；
- [ ] 控制台无未捕获错误；
- [ ] `engine.js` 不新增济南专属地标 ID 或中文文案硬编码。

## 13. 风险与依赖

| 风险 | 影响 | 处理 |
|---|---|---|
| AI 图片建筑层数、泉眼数量错误 | 济南用户一眼识别为假 | 每张母稿按识别特征清单复核，错误先修母稿再导出 |
| 每个页面独立生成图片 | 画风和地标外形漂移 | 强制共享母稿与固定目录，只允许派生尺寸 |
| 为了“真实地图”把内容塞得过密 | 地图不可玩、地标看不清 | 总览负责结构，区域地图负责漫游，明确不用于导航 |
| 图片先做但未实装验证 | 透明边、尺寸、移动端显示问题延后暴露 | 每批图片完成后立即接浏览器检查 |
| 路线继续硬编码 | 第二章接入时复制逻辑 | 章节与路线数据化作为 P0-B 前置 |
| 旧拼豆代码和数据继续影响 UI | 产品主线混乱 | UI 全下线；代码可延后清理，但不得加载或展示 |
| 素材许可不清 | 开源发布风险 | 生成/参考过程与许可同步记录，不在发布前补账 |

## 14. 发布门槛

以下任一项未满足，不得称为“济南六章节 MVP 成品”：

1. 六章节总览仍使用旧 `map.png`；
2. 两章共享同一张区域地图或同一张明信片底图；
3. 超然楼、趵突泉、黑虎泉无法在无文字情况下区分；
4. 任一正式图片仅存在临时目录、聊天附件或外链；
5. 四个锁定章节点击无反馈；
6. 第一章能玩、第二章只是静态封面；
7. 下载明信片与玩家本章收集结果无关；
8. 页面仍公开拼豆入口；
9. 未完成移动端真实浏览器验证；
10. 未记录图片许可与来源。
